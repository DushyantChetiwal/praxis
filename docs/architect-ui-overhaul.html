pub fn render_workspace(view: ArchitectView) {
    // Architect owns the primary application surface.
    match view.workspace() {
        Workspace::Architect => render_plan_workspace(),
        Workspace::Code => render_code_workspace(),
    }
}

fn render_code_workspace() {
    project_panel()
        .with_editor()
        .with_terminal()
        .with_plan_conversation();
}

What this overhaul changes

This is an application-shell change, not a sidebar redesign. Plan state, project state, and conversation state must survive seamless switches between two complete workspaces.

1

Persistent plan navigation

A semantic outline complements the canvas and exposes readiness without relying on spatial memory.

2

Structure-first canvas

Cards show responsibility, state, and handoff metadata—not every editable field at once.

3

Context-specific inspector

Details, conversation, and execution each receive a purpose-built right panel.

4

Distinct execution mode

Progress appears consistently across the header, outline, graph, and live timeline.

5

Two top-level workspaces

Architect is the default application surface. Code is a full alternate workspace, not a collection of temporary drawers around the graph.

6

Shared plan continuity

The Code workspace keeps the overall plan conversation, selected step, run state, and project context connected.
